# Architecture

NaijaPrep is a low-bandwidth exam-practice PWA for JAMB/UTME, WAEC/NECO and
Post-UTME students. Phase 2 moved the app off Express/PostgreSQL/JWT onto
Vercel Functions and Firebase.

## Runtime shape

- **Frontend:** React 18 + Vite SPA built to `frontend/dist`. It uses the
  Firebase Auth client SDK only; it never talks to Firestore or Storage directly.
- **API:** Vercel Functions in `api/`, Node runtime. Routes use Zod validation,
  a consistent error envelope, request IDs, structured logs and CORS allowlists.
- **Auth:** Firebase Auth (Google and email/password). `requireUser` verifies
  every ID token with the Firebase Admin SDK. Client-sent user IDs are ignored.
- **Data:** Firestore, accessed only by the Admin SDK from `api/`.
  `firestore.rules` denies all client reads/writes.
- **Files:** Firebase Storage is reserved for future media. Direct client access
  is denied; any future download will use short-lived server-issued URLs.
- **Push:** Firebase Cloud Messaging web push plus a Vercel Cron sender are
  planned, not part of Phase 2.
- **Offline:** Phase 3 will add a service worker, compact bundles and an
  IndexedDB retry queue. The current app works online only.

## Trust boundary

```
Browser
  |  Firebase ID token (Authorization: Bearer ...)
  v
Vercel Function (api/) -- Firebase Admin SDK --> Firestore
  |
  +-- Zod validation + CORS + App Check hook
  +-- answer keys never serialized to public responses
```

The browser supplies only an exam ID, a client-generated session ID and answer
choices. The server derives the UID from the verified token, loads the exam,
scores the attempt and writes the result. No client-supplied score, UID or
correct answer is accepted.

## Data model

### `exams/{examId}`

```ts
{
  title, subject, examType, durationMinutes,
  published, sample,
  questions: [{
    id, text, options: string[], correctOption, topic, explanation?
  }]
}
```

Embedding questions means a mock start needs one exam read. `POST` and public
`GET` mappers return `text`, `options` and `topic` only; `correctOption` and
`explanation` are reserved for the post-submit review. `parseExam` validates all
content before serving it and rejects malformed documents with a 500 error.

### `users/{uid}`

A single profile document holds:

- identity fields (`username`, `email`, `displayName`, `photoURL`, timezone),
- denormalized `stats`,
- `progress` keyed by subject,
- the latest ten `recentAttempts`,
- preferences such as `leaderboardOptIn`.

The dashboard reads one document. `ensureProfile` creates a default profile
lazily on first authenticated request.

### `users/{uid}/mockSessions/{sessionId}`

Session IDs are generated by the client (`crypto.randomUUID` with a fallback)
and validated by Zod. A session stores `examId`, `status`, start/expiry times,
question count and, after submission, the full result. Reusing an ID is
idempotent: an in-progress session is returned unchanged, and a completed
session returns its stored result without rewriting stats.

## Write path

Submitting uses one Firestore transaction:

1. Read the session; if completed, return the stored result.
2. Read the exam and score the submitted answers server-side.
3. Read the profile.
4. Update the session to completed with score, review and result.
5. Update stats, subject progress and recent attempts on the profile.

This prevents double-counting on retries and keeps the dashboard consistent with
the session record.

## Read budget (Spark tier)

| Screen/action | Firestore reads | Firestore writes |
| --- | --- | --- |
| Dashboard/profile | 1 | 0 |
| Start mock | 2 (session existence + exam) | 1 |
| Submit mock | 3 (session + exam + profile) | 2 |
| Exam list | 1 per cache miss, CDN cached for 5 minutes | 0 |
| Attempts history | 1 per page | 0 |

A fresh mock is approximately 6 reads and 3 writes including the dashboard
refresh. Sample content has 5 questions per exam so bundles stay small.

## Composite indexes

`firestore.indexes.json` covers:

- `exams`: `published ==`, order by `subject`, `title`, `__name__`.
- `mockSessions`: `status ==`, order by `completedAtMs desc`, `__name__ desc`.

Deploy with `firebase deploy --only firestore:indexes`. The emulator does not
enforce missing indexes, so this step is required for production.

## Security controls

- Deny-all Firestore and Storage rules, verified by `npm run test:rules`.
- Firebase Admin token verification on every protected route; revoked-token
  checks available via `requireUser` options.
- App Check hook enabled with `appCheck: true` on protected routes and enforced
  only when `APP_CHECK_ENFORCE=true`.
- CORS allowlist for browser writes; uniform request IDs and error bodies.
- No AI model or provider in the critical path. Explanations are static content.
